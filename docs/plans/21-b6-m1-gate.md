# B-6 (item 74): M1 gate — minimum playable demo, verified end-to-end

PLAN.md item 74 is the milestone acceptance test: *"a minimum playable demo —
one converted map, a player mob that spawns, moves, and interacts with one
object, visibly rendered, in a running server."* This document records the
demo corpus, the gate, the integration seams it exposed, and what is still
unproven.

## The demo corpus — `tests/m1-demo/`

A hand-built DM world, deliberately minimal:

- `code/m1.dm` — `/turf/space|floor|wall` (iconned), `/obj/m1_button` with a
  `Click()` that bumps a counter and emits `usr <<` + `world <<`, a `poke`
  verb on the same object, `/mob/living/carbon/human` (iconned; the B-1
  player-mob proto preference picks it), `step_north`/`step_east` mob verbs
  that write `x`/`y`, and `world/New` logging.
- `icons/m1.dmi` — real DMI (PNG + tEXt metadata), five 32×32 1-dir/1-frame
  solid-color states, generated by `tools/make_dmi.mjs` (committed binary).
- `maps/m1.dmm` — TGM room: space border, wall ring, floor, button at DM(4,5).

## The gate — `scripts/m1-gate.sh`

`convert → dotnet build → boot server → headless client → assert`. Each M1
element reports `PASS`/`FAIL` with a grepable evidence line; exit 0 only on
all-pass. Modeled on `client-smoke.sh` (shared engine-obj `-m:1` retry loop,
Robust.Client XAML re-embed pass).

| Element | Assertion | Evidence |
|---|---|---|
| E1 map loaded | `World init: loaded map`, `Registered N converted tile definitions`, `minted turf datums`, `M1-WORLD` | server log |
| E2 connect+attach | client `Runlevel changed to: InGame`/`Received Full GameState`, server `attached to mob` | both logs |
| E3 visible render | `entfo {attached}` dumps `SpriteComponent` `vis=True` with a live layer (`state=human`, `UseSpriteStrategy`); `dumpentities` contains `obj_m1_button`; zero `Unable to load RSI`/texture errors | client log |
| E4 movement | `dmloc` coords change after `dmverb step_north`/`step_east` (x=1,y=1 → x=1,y=2 → x=2,y=2); server `M1-MOVE:` lines | both logs |
| E5 interaction | `dmclick /obj/m1_button` fires `Click()` → `M1-CLICK:` in server log and `M1-CLICK client:` in the client console; `dmverbon ... poke` likewise | both logs |

## New mechanism: the client autocmd channel

The engine's client console never reads stdin (`SystemConsoleManager` is
server-only), so a headless `--connect` client can never type a command —
there was previously no way to drive dm* commands *as the player session*.
The generated client EntryPoint (ss14Template) now reads
`Resources/autocmds.txt` (one command per line; `{attached}` substitutes the
mob uid) in `Init()` — a content-file, since `Environment.GetEnvironmentVariable`
is sandbox-banned — and in `Update()` fires each line via
`IClientConsoleHost.ExecuteCommand` once `SessionStatus.InGame` (+2s settle,
1s per command). This is the same path a player typing in the debug console
takes: server-registered dm* commands arrive as `ServerDummyCommand`s and
forward as `MsgConCmd` executed server-side with `shell.Player` = the
session, so `usr` binds to the attached mob.

## Seams found and fixed

1. **Map load threw `KeyNotFoundException: key '0'`** (`mapConverter`).
   Chunk blobs are a full 16×16 grid; cells outside the DMM region stay
   yaml-tile-id 0 and `MapChunkSerializer` resolves *every* cell through
   `tileMap[id]`. Fix: `tilemap` now always emits `0: dm_space` (stock maps
   convention) and `yamlGenerator` always emits a `dm_space` dmTile proto —
   sprite-less so out-of-map cells render as space; `RegisterGrid` mints a
   generic `/turf` datum for them (BYOND `world.turf` default semantics).
   *Before this, NO converted map ever loaded on the real engine.*

2. **`DMAppearanceKey` could never serialize** — `KeyNotFoundException` in
   `PvsSystem.SendGameStates`, killing the server on the first state send.
   `RobustSerializer` only indexes `[NetSerializable]` types from module
   assemblies; the enum lived in `SS13.DM.Runtime.dll`. The B-3 sibling fix
   (PR #14, merged into this branch) moved it to `Content.Shared/DM/
   DMAppearanceKey.cs`; an identical in-flight fix here was dropped for
   theirs (emit-side `Shared.props` injection + `using Content.Shared.DM;`).

3. **`Environment.GetEnvironmentVariable` is sandbox-banned** — the first
   autocmd iteration read an env var and the client type-checker rejected
   `Content.Client.dll` outright. Replaced with the `autocmds.txt` content
   file (see above).

4. **Deferred `JoinGame`** (from #14): sessions queue into `_pendingJoins`
   and join on the next `Update` tick so the client sees `Connected` ≥1
   game-state before `InGame`. Verified working in this gate.

5. **`Eye` on /mob protos** (from #14): the attached mob now carries a
   camera — `entfo` shows `EyeComponent` on the player mob.

## Verified

- `bash scripts/m1-gate.sh` → **5/5 PASS** (twice: pre- and post-merge).
- `npm run build` clean; `npm test` green incl. new item-74 assertions

## Windowed render evidence (the final inch)

After the headless gate passed, a real windowed `Robust.Client` (llvmpipe
GL 4.5 on a VNC box) was driven against the gate's output world. Pixels
captured: the green `human` mob sprite and the red `m1_button` sprite render
at correct map positions (offsets match `dmloc` coordinates × 32px/tile).
Keypress-driven `Command` binds fired `dmverb step_north`/`step_east` and
`dmclick /obj/m1_button` on camera — the mob sprite moved and `M1-CLICK`
output appeared in the debug console on screen. "Visibly rendered" is
proven, not just resolvable.

Notes folded back into the template from that run:

- `Resources/keybinds.yml` is now emitted (was missing entirely —
  `ShowDebugConsole` had no bind, so the console could never open
  windowed). `KeyBindingType` at this pin is `State|Toggle|Command`; a
  `Press` bind crashes the client at startup.
- A lighting-free world renders black client-side (real semantics —
  `MapComponent.LightingEnabled`); evidence capture used a networked
  `PointLight` on the mob proto and/or `drawLight: false` on the mob `Eye`.
- llvmpipe frame stall reproduces with lighting on (~10-15s then freeze);
  `drawLight:false` + `LP_NUM_THREADS=2` + `xrandr -s 1024x768` mitigates.

## Known limits (honest)

- **Client-side tile drawing gap**: `dmTile` defs register server-side
  only; `ClydeTileDefinitionManager` builds its atlas at `IPostInjectInit`
  (before content protos load) and only regenerates on `/Textures/Tiles`
  changes. Observed windowed: turfs draw *nothing* (skipped, not
  error-textures) even fullbright — entities render normally over them.
  Engine-internal, not a small seam.
- Console `LineEdit` doesn't submit under synthetic input (special keys
  swallowed) — `Command`-type keybinds on the same `ExecuteCommand` path
  were used for live input.
- `[usr.name]` interpolates empty in `M1-CLICK:` — the datum `name` var
  isn't seeded from the type's `name` initializer on the spawned mob datum.
  Cosmetic; output path itself proven.
- Disconnected-session mobs persist on the map across relaunches
  (BYOND-consistent; cosmetic).
- B-3's flagged pre-existing blockers stand: `..()` re-resolution stack
  overflow, `RegisterSubsystems` off-thread CallProc, oversized-paradise
  dmTiles vs the 32px atlas rule, no ambient light (world blacks out —
  semantics, per above).
